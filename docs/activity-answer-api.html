有奖问答接口文档

覆盖后台活动配置、数据分析、答题记录、发放记录，以及小程序详情、开始答题、单题提交、任务、我的记录和奖品地址。

基础约定

后台前缀/admin-api/promotion/activityAnswer

小程序前缀/app-api/promotion/activity-answer

统一响应{ "code": 0, "data": {}, "msg": "" }，类型为 CommonResult<T>。

活动类型ActivityTypeEnum.ANSWER = 9；推广渠道枚举当前代码为 ActivityChannelTypeEnum.DT = 13。

会员口径小程序端不依赖前端传 memberId。答题次数、任务次数、继续答题、奖励查询统一按 memberMobile 归属，memberId 仅作为快照字段。

答题方式/submit 为单题提交接口。每答一题提交一次，最后一题提交后统计正确数并发放奖励。

题目配置走缓存；用户当前场次答题记录和明细直接查库。开始答题时会把当时的全部题目写入 activity_answer_record_detail，后续继续答题、题目分析、导出都以这批明细为准。

小程序浏览埋点：PV / UV

POST /app-api/analysis/event/add

复用营销通用埋点接口。此路径属于 analysis 服务，不拼接 promotion/activity-answer 前缀；网关前缀沿用项目现有配置。

请求头使用 Content-Type: application/json，business-id 与活动归属项目一致，其他登录及租户请求头沿用小程序请求封装。

请求示例

{
  "from": 1,
  "eventType": "answer",
  "eventId": "190000000000000001",
  "storeId": "190000000000000002",
  "memberId": "190000000000000003"
}

示例ID需替换为当前活动、门店及会员的真实ID；长ID始终按字符串传递，避免JavaScript精度丢失。

字段类型接入要求说明
fromInteger传入微信小程序传1；支付宝传2。
eventTypeString传入固定answer，后台以此统计问答页面PV/UV。虽然现有枚举名称写“参与”，这里代表页面浏览，不要每答一题再发。
eventIdString传入统一取小程序/detail响应的data.activityId。不要传题目ID、答题记录ID，也不要同时用问答配置ID和活动ID各报一次。
storeIdLong，JSON字符串传入当前访问门店ID。
memberIdLong，JSON字符串传入当前会员ID，UV按该字段去重。通用接口不会自动从登录态填充此字段，与答题业务接口的入参规则不同。不要传手机号、openid、空值或统一的0。
channelString可选有推广渠道则传实际渠道；不传或空白时后端默认1000000002。
timestampDate建议不传不传时使用服务器当前时间，避免客户端时间偏差和月份索引错位。
businessIdLong不需要传后端从项目上下文覆盖填充，不能通过请求体切换项目。

以上“传入”为本场景的前端接入约定；现有通用BaseEvent没有对这些字段逐项加非空校验。

响应

{ "code": 0, "data": true, "msg": "" }

成功代表已交给现有批量写入器，不能据此认定ES已经落库。批量刷新间隔默认3秒（可配置），查询还受ES刷新影响，统计可能短暂延迟。

上报时机与统计口径

  • 活动详情成功加载且页面实际展示、会员ID就绪后，每次访问上报一次。详情轮询、答题提交和普通刷新不重复上报；真正离开再进入可计为新访问。
  • 同一会员进入两次：PV增加2，UV增加1；另一位会员进入一次：合计PV为3、UV为2。每日UV按当天去重，活动周期UV按整个查询区间去重，不能把每日UV直接相加。
  • PV和UV使用同一条answer事件，不需要再发送独立的UV事件。UV使用现有ES cardinality聚合，是近似去重统计。
  • 现有接口没有请求幂等键，每次上报生成新ES记录；不要在onLoad和onShow同时上报，也不要在请求超时后无限重试。
  • 没有会员ID时现有方案无法区分匿名访客。匿名UV需要另行设计稳定访客标识，不能用0代替所有访客。
  • 埋点请求独立于详情和答题请求，前端埋点失败不阻止用户继续答题。

后台查询与联调

后台现有 GET /admin-api/promotion/activityAnswer/getActivityAnswerAnalysis/{id} 返回 pvCount/uvCount（同时提供pv/uv）；POST /admin-api/promotion/activityAnswer/getActivityAnswerDailyAnalysis 返回dateList、pvValues、uvValues。浏览统计查询event_logs_yyyy-MM索引，按businessId、eventType=answer、eventId和时间区间过滤。

上报统一使用活动ID，后台查询继续沿用原有配置ID入参约定。概览目前使用活动起止日期作为统计窗口，窗口外的事件不计入概览。

联调使用同一活动：会员A访问两次、会员B访问一次，等待批量写入与ES刷新后核对PV增加3、该区间首次访问的UV增加2。需同时确认项目ID、活动ID和统计时间范围一致。

现有埋点写入业务直接交给ES批量写入器，不新增MySQL业务查询或事务。当前通用接口允许匿名调用、memberId来自请求体，统计属于客户端上报口径，不作为发奖或扣次数依据。

Key说明
