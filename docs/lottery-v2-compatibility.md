# 抽奖 V2：旧活动兼容与 Redis 热路径

2026-09-28。本轮覆盖旧活动重新启用，以及减少抽奖热路径的数据库访问，不代表整体改造计划全部验收完成。

## 旧活动重新启用

- 历史活动保持 `runtime_version=1`，不批量迁移。仍启用的旧活动继续走原抽奖、列表、详情和保存逻辑；旧抽奖记录、任务机会、奖品 `remain_num` 保留。停用后重新启用才初始化并切换到 V2。
- 首次重新启用，在同一事务和配置行锁内补齐缺失的奖品 code/模板，创建新 `stock_epoch`，按奖品配置总量建账，`reserved/issued=0`。V2 次数首次使用时从零初始化，不导入旧消耗。
- 保留已有非空 code、奖品 ID 和旧消耗；共享奖池兼容旧 `store_id=NULL/0`，独立奖池按门店建账，也包含暂时移出门店的已有奖品。
- 已有 V2 库存、次数或流水但仍标记旧版时拒绝初始化，避免覆盖已有数据。初始化失败整体回滚。重复启用及 V2 活动停用再启用不再次清零。
- `/promotion/lottery-log/updateState` 使用活动 ID + `isEnabled`；旧 `/updateLotteryState` 使用配置 ID + `state`。两个入口及通用活动启用入口统一调用生命周期服务。
- 新版修改接口携带 `isEnabled=1` 也必须初始化，保存后两个启用状态保持一致。修改 V2 奖品总量只校验新账本，不再被旧 `remain_num` 限制。
- 旧退奖仍处理旧数据，不增加 V2 库存；V2 退奖使用原流水批次。场次定时重置只处理 V2，不静默重置历史活动。
- 上线前停止旧实例受理并等待旧抽奖在途任务完成，禁止新旧实例同时受理同一活动；不要求删除历史领奖记录。

## Redis 与数据库分工

- 库存 Redis Hash 包含 `total/used/revision/configVersion/pending`。热缓存直接 Lua 预占，不再每次预占前、受理成功后各查询一次库存账本。
- 预占同时写随机 `pending` 令牌，数据库成功受理后只清除本次令牌。若进程中断，下一个持锁请求发现令牌后，先从持久化账本恢复该分区再预占。
- 缓存缺失、配置版本变化、缓存内容异常同样触发受控恢复；账本缺失拒绝受理，不默认满库存。Redis 故障不放行新抽奖。
- Redis 确认失败不能撤销数据库已受理请求；保留异常标记或缓存缺失状态，后续恢复。重复受理或事务失败必须核对库存，不能直接确认重复预占。
- 发奖成功的 `RESERVED -> ISSUED` 不改变总占用，不再查库同步库存；释放和退奖仍按原库存分区恢复后完成持久化任务。
- 移除抽奖服务与接口前置结果查询重复的流水查询。新流水插入后用已知数据生成返回值，省去立即重读和反序列化。无奖品次数解锁门槛时不读取活动累计次数。
- 次数继续使用 Redis 快照、版本及持久化刷新任务。数据库保留请求唯一约束、短事务、次数条件更新和库存条件更新，保证最终不超发。
- 正常热库存预占及确认：库存账本读取 **0 次**；缓存缺失或中断恢复：按分区读取 **1 次**。整次抽奖仍有必要的防重、配置检查和持久化写入，不是零数据库操作。

## 验证

- JDK 17、Maven 离线编译通过；42 项抽奖回归通过，失败/错误均为 0。
- H2 MySQL 模式覆盖新批次与历史数据保留、跨项目隔离、8 次并发启用仅初始化一次、重复启用、回滚、库存与流水一致性。
- Mockito 覆盖热库存零账本读取、冷缓存一次读取、锁竞争快速失败、账本缺失拒绝、重复/不确定受理恢复。
- 执行生产预占/确认 Lua（LuaJ 模拟 Redis 命令）：1000 个请求争抢最后一份库存仅一个成功；覆盖中断标记、令牌校验、配置变化和异常库存。
- 验证后删除临时测试源码，保留 `.lottery-compat-build.log`、`.lottery-compat-tests.log`。
- 未连接业务数据库、未执行 SQL、未调用真实微信。上述验证不替代真实 MySQL/Redis Cluster 压测，接口 P95/P99 和全国容量需在部署环境验证。
