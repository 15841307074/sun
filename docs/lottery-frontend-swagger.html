本轮变更范围

前端优先接入：requestId 防重、标签适用范围。 新增接口为小程序 POST /result、GET /recent-winners，以及后台 POST /lottery-log/reissue 人工补发。本轮响应保留 requestId/grantStatus，不输出内部抽奖处理状态。

lottery 直接返回奖品。 code=0 且有奖品数据时完成本轮中奖展示，后台异步发放；用户下一次真实抽奖生成新 requestId，不必等待上一轮发奖。

result 只查询，reissue 才安排人工补发。 后台补发有独立权限，不再次扣次数或消耗积分。不要将查询接口当作补发操作。

适用于 PC 活动配置与小程序抽奖页。可离线打开，支持搜索、折叠和复制 JSON。示例 ID/图片为示意值。

代码基线 HEAD 4fbb6c2d7，包含响应字段移除和人工补发的本地修改；核对日期 2026-10-08。正常抽奖已有的红包失败转兜底逻辑保留；人工补发独立处理失败，不再次换奖。

前端调用顺序

1 · 进入抽奖页加载 getLotteryDetailApp、lotteryNum 和 recent-winners。
2 · 点击抽奖生成 requestId，保存本次上下文，可沿用 verifyLottery，再调用 lottery。
3 · 展示中奖结果lottery 成功返回奖品后完成本轮动画和结果展示；后台异步发奖。
4 · 再抽或按需查询再抽生成新 ID；网络异常恢复或红包领取时，用原 ID 调用 result。

后台：列表 → getByDetail → 标签选择器 → 完整表单保存/编辑 → 单独 updateState → 刷新列表。

当前限流规则（V2）

以下为 LotteryProperties 的代码默认值，也与 Nacos 示例一致；实际环境可能被 promotion.lottery 配置覆盖，本文件未读取线上 Nacos。这里统计请求速率和正在执行的请求，并非每天可抽次数；每日/场次/活动总次数是另一层业务规则。

限制默认值作用范围配置项
新抽奖请求100 次 / 1 秒窗口所有实例共用的 draw 入口 Redis 计数draw-rate
单活动新抽奖请求60 次 / 1 秒窗口同项目 + 同活动，所有实例共用activity-draw-rate
单会员新抽奖请求1 次 / 1 秒窗口同项目 + 同活动 + 同会员；不是会员所有活动合计member-draw-rate
结果查询请求300 次 / 1 秒窗口所有实例共用的 result 入口；lottery 内部查重也使用此入口result-rate

Redis 计数从该键第一次请求开始，设置 1000ms 过期；不是按自然时钟整秒归零，也不是严格滑动窗口。请求超过窗口上限会拒绝；被拒绝的请求也可能已经增加前面步骤的计数，不应连续立即重试。

默认 connection-budget=16、grant-concurrency=4，再保留 4 个名额，普通请求共享可用预算为 8；详情/任务与新抽奖的瞬时并发还会受该共享预算影响。正在异步发奖的整段等待时间不占着新抽奖请求的执行名额。

防重与限流是两件事：相同 A 已受理时，重发 lottery 优先查询并返回 A，不再作为新 draw 扣次数，也不进入新 draw 速率检查；但查询仍受 result 速率和并发限制。新的 B 会重新经过全局、活动、会员三层新 draw 限流。上一轮已经完成，也不意味着这些限制自动解除。

限流/并发拒绝返回业务 code=1006000006（目前参与人数过多）。在受理前被拒绝不会扣抽奖次数或预占库存。建议退避重试；A 的结果未知时仍只使用 A，不换 ID。持续运行的旧活动不自动套用 V2 新 draw 这组限流。
