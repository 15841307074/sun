# 发奖触发与空闲查库优化

新抽奖、人工补发、有效红包回调及实物退奖在任务写入成功后发送进程内通知。Spring 事务中的通知提交后才执行，回滚不执行；无事务场景在持久化更新后执行。普通奖品由原发奖线程池执行。红包按原立即领取契约，在 lottery 返回前准备微信转账单和领取参数，实际确认到账继续由用户确认、回调及后台处理。

## 红包沿用原领取流程

新版构建 `LotteryRedPacketVo`，提供 `activityId`、固定 `outBillNo`、OpenID、分为单位的金额、转账备注和场景报告。复用 `LotteryRedPacketService.transferUser` 的固定单号入口：短事务保存转账记录并抢占首次发送权，首次直接 POST；重试先查微信原单，只有原单明确不存在且首次发送已超过保护期时才同单号发送。领取参数准备时先释放库存 Redis 锁，不持有库存锁或数据库事务等待微信。

`lottery` 正常红包返回 `grantStatus=WAIT_USER_CONFIRM`、`packageInfo` 和 `outBillNo`，原立即领取按钮直接使用这些参数，不需要正常流程额外轮询 `result`。现金任务仍有十五秒延迟的持久化恢复通知；正常准备完成后移除多余的内存唤醒，微信处理中则沿用原单重试。

微信尚未返回有效领取参数时，`lottery` 返回 `1006005031`，原中奖流水和未领取记录保留，须使用同一个 `requestId` 重试本次 `lottery`，不能当作新抽奖另建 ID。明确失败但仍为红包奖品时返回 `1006005032`；原普通抽奖明确失败仍可切换兜底奖品，转账结果未知时不盲目释放库存或换支付单号。`result` 保持只查询，不发起转账或补发。

红包受理流水和任务先持久化；微信返回后一次写入带领取参数的抽奖记录，减少正常返回路径中的重复记录读写和中间状态事务。微信异常时仍保存未领取记录；成功后更新领取状态。切换兜底后记录同步为当前兜底奖品，迟到的旧补发不能覆盖新单号。

服务就绪时预加载客户端和密钥，不查询微信、不发起付款；首次网络连接的 DNS/TLS 和微信处理耗时仍可能存在。`lottery.cash.wechat.duration` 分别记录发送和查询耗时。`lottery` 仍在有效领取参数准备完成后返回，保持前端立即领取契约。

正常领取任务先做带次数上限的原子租约更新，成功后不再额外执行停止状态更新。红包跳过仅实物退奖需要的任务类型查询，并复用发奖过程已读取的当前流水；未取得租约时仍重新读取原单。转账记录准备与首次发送权合并在同一个短事务，事务提交后调用微信。重试次数上限、租约接管、固定单号和失败恢复保持不变。

### 定位红包慢请求

超过 500ms 的对应阶段才输出 INFO 耗时日志，不增加数据库查询。按 `requestPk` 或 `outBillNo` 核对同一笔请求：

- `红包受理耗时`：`validationMs` 包括会员/资格和奖品准备，`acceptMs` 为库存预占、账本受理及提交后缓存更新。
- `红包处理耗时`：`totalMs` 为发奖准备总耗时，`transferMs` 包括转账记录准备、微信调用和保存微信结果，`localMs` 为其余领取、记录及任务状态处理。
- `红包微信接口耗时`：`operation=send/query` 的 `elapsedMs` 为实际微信请求耗时，不包含本地账本和记录准备。

结合现有接口访问日志的总耗时，可以确认延迟属于受理、数据库/记录处理、微信还是接口之外的页面等待。没有部署后的分段数据时，不能把稳定约两秒直接归因于微信，也不能保证本地优化后达到固定响应时间。日志不输出 OpenID、领取 package、手机号或支付密钥。

配置和次数缓存的空闲补查已取消，失败保留记录与日志；发奖持久化恢复和租约接管继续保留。

## 缓存与数据源

积压快照过旧本身不再被判为人数过多。异步刷新继续按两秒共享期限合并；首次缺失快照时八实例合计仅放行一个受控请求，已有暂停快照仍拒绝新抽奖。积压拒绝不消耗会员当秒的抽奖限流额度，真实高低水位保持一百笔暂停、三十笔恢复。

新增抽奖类已移除强制 `master` 注解和后台切换，沿用当前调用链或环境默认数据源；发奖、延迟任务、缓存发布和门店通知跨线程保留提交时的数据源上下文，连接池保护检查相应数据源。数据库地址由各环境配置决定，UAT 和生产均须在各自实际使用的库完成现有表结构。移除注解不创建表，也不解决缺列或旧部署包问题。

线程池使用 64 条有界等待队列，等待任务只保存任务 ID、不领取数据库连接。进程内去重防止同一个任务重复排队。队列满或通知无法交付时，任务仍在 `lottery_v2_job` 中，后续补查恢复。

失败重试仍按数据库的 `next_at` 等待十秒；进程内记录唤醒时间，期限到达才尝试领取。延迟通知最多保留 1024 条，超出后改由持久化任务补查。SQL 更新未持有有效租约时不发出重试通知。

每秒定时动作只检查内存时间和连接池指标，不代表每秒查询数据库。启动后第一次检查遗留任务；空闲时约每五分钟检查一次，再加 0～30 秒随机间隔错开八实例。发现一批待办已取满，或本机排队溢出时，允许约一秒后继续补查；发奖线程已满或连接池余量不足时不执行这次 SQL。数据库异常后退回低频检查，不在空闲时连续一秒重试。

保留低频检查是为了多实例故障接管：某实例提交后退出、通知丢失、执行租约过期，都能从持久化表恢复，不依赖用户再次点击。正常新任务无需等待该检查。八台空闲时原先约每分钟 960 次待办查询，现约每分钟 1.5～1.6 次；这是频率估算，实际还取决于连接池是否允许检查。

各实例继续通过原数据库条件更新领取租约，原 requestId、次数、积分业务号、库存事务和发奖幂等约束不改变，不新增表、外部消息队列或 Nacos 参数。

## 给其他业务留余量

运行时识别本次任务使用的数据源的 Hikari/Druid 连接池，不借连接、不执行 SQL，只读取内存指标。发奖线程上限取现有配置上限、连接预算一半、连接池最大连接数四分之一三者的最小值（至少一个线程）。

当主库的可用连接进入预留区时，后台停止领取和补查。预留区约为连接池四分之一，常规池至少留两个；极小池最多保留到还剩一个连接。线程池等待队列不占连接。此检查是并发控制及避让机制，不会建立物理独占连接，也无法限制其他业务自行取连接。

不识别的连接池或数据源切换期间，继续受原配置预算约束；部署时仍须核对实际池大小，以及所有服务合计连接数。推荐的八实例起点见 `lottery-eight-instances-nacos.example.yaml`，默认代码配置不变，未修改实际 Nacos。建议先验证每实例池占用、待办增长速度及响应耗时，再调整。

营销模块及依赖编译通过；50 项隔离回归通过，包括 14 项新验证：事务提交/回滚、主动触发、重复通知、十秒延迟、空闲低频、错峰、队列满后恢复、两实例租约竞争、启动恢复、数据库故障退避和连接池繁忙避让。测试不是实际八实例压测，尚未部署或重测线上环境。
