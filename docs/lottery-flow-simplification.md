# 抽奖流程审查与精简（2026-10-12）

本轮保持原有接口路径、字段和抽奖规则。普通抽奖仍按 requestId 防重复、受理时固定奖品快照，发奖继续异步执行；结果查询不扣次数、不触发补发；人工补发沿用原记录，不再扣次数和消耗积分。旧活动仍须从管理端重新启用后初始化新版运行批次，原中奖历史不清空。

## 表结构

营销侧 V2 运行表由 7 张减少为 5 张，不新增表：

| 保留的表 | 职责 |
| --- | --- |
| `lottery_v2_request` | 请求幂等、确定奖品快照和发奖结果 |
| `lottery_v2_stock` | 库存预占、已发放数和退奖核对 |
| `lottery_v2_counter` | 会员次数、活动总抽奖数、次数缓存待刷新标记 |
| `lottery_v2_job` | 发奖、补发和退奖的异步重试及执行租约 |
| `lottery_v2_cache_task` | 配置版本发布与旧展示缓存清理的失败恢复 |

`lottery_v2_activity_counter` 并入次数表的内部行：`member_id=0, scope_key=ACTIVITY_TOTAL, source=0`，`gained` 保存原活动总数。该行不出现在会员次数查询中。它仍在原受理/失败退次事务内加减，不重新按历史流水求和。

`lottery_v2_counter_cache_task` 并入会员的 `scope_key=TOTAL, source=0` 次数行，只增加 `cache_dirty`、`cache_next_at` 两个内部字段和发布索引。计数改变时标记待发布；后台每次最多处理 64 行，成功后按原 revision 条件清除标记。并发期间产生新 revision 时，旧任务不能清除新任务，也不能把新任务推迟。

配置发布队列保留独立表：配置删除、奖品删除和版本切换后仍需恢复 Redis 发布，不能只依赖内存通知。请求、库存、次数和发奖任务也保持数据库约束，避免重试时重复扣费、重复发奖或超发。

## 流程改动

普通奖无库存后转兜底，与普通奖共用相同的提交确认和重复请求恢复分支。若兜底受理遇到重复键或提交结果不确定，会查同一个 requestId 的持久化记录；已有记录返回原结果，没有记录仍返回真实异常。

配置缓存清理时，门店列表由重复查询两次改为查询一次。接口的限流、Redis 缓存、活动和门店范围校验、奖品选择、次数来源、积分扣退以及人工补发规则不改变。

## 接口核对

| 接口 | 保持的行为 |
| --- | --- |
| `/lottery` | 新 requestId 才产生新抽奖；网络重试复用原 requestId |
| `/result` | 查原抽奖结果；不重新抽奖、不重新扣次或补发 |
| `/lotteryNum`、`/task/getTaskList` | 展示原规则下的次数和任务 |
| `/task/share`、`/task/browse` | 按原周期、来源和上限增加机会 |
| `/recent-winners` | 保持最新中奖展示及手机号脱敏 |
| 管理端人工补发 | 权限、原奖品、原会员/门店校验保持；不重新扣次和积分 |

## 升级

使用已有 `sql/lottery_release_all.sql`，执行 PROMOTION 部分。先暂停旧版本抽奖入口、发奖及缓存发布任务；脚本增加两个字段、索引，并将旧辅助表中的 V2 数据和待发布标记迁入次数表，然后整体切换新服务。新安装不创建两个旧辅助表。

活动汇总用 INSERT IGNORE 迁移：已存在的新汇总行不会在脚本重跑时被旧值覆盖，避免退款后重新增加历史总数。待发布标记保留在主库，不受 Redis 故障影响。旧辅助表仅用于升级读取，运行代码不再访问；本脚本不自动删除旧表，核对并备份后再删除。未连接或修改实际数据库。

保留的 5 张表可支撑原流程，无需引入新的队列、数据库表或依赖。原前端文档继续适用，无需改变请求或解析代码。
