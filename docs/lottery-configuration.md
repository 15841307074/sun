# 抽奖配置精简

`LotteryProperties` 的 14 项原先都有引用。本次将 3 项缓存有效期、1 项配置缓存回源并发收进缓存实现，外部配置减少到 10 项。活动配置、奖品和结果缓存按活动结束时间加七天过期；门店列表以版本发布主动刷新，五分钟过期兜底。保持限流默认值、回源保护和结果缓存的补发版本校验；不改接口、扣次、积分或发奖流程，不增加表。

日常只需在 Nacos `promotion-server.yaml` 的 `promotion.lottery` 下覆盖需要调整的项。简版见 `lottery-v2-nacos.example.yaml`，未填项使用代码默认值。Nacos 的命名空间、分组和应用环境须一致；保留现有其他配置。仍支持配置刷新，发奖线程数在后台轮询时调整。

| 配置项 | 默认值 | 用途 |
| --- | --- | --- |
| draw-rate | 100 | 所有实例共享的新抽奖请求每秒上限 |
| activity-draw-rate | 60 | 同项目、同活动的新抽奖每秒上限 |
| member-draw-rate | 1 | 同项目、同活动、同会员的新抽奖每秒上限 |
| result-rate | 300 | 查询原结果/抽奖查重每秒上限 |
| query-rate | 1000 | 普通查询接口共用每秒上限 |
| task-rate | 200 | 任务接口共用每秒上限 |
| accepting | true | false 只暂停新抽奖，已受理发奖继续 |
| draw-concurrency | 8 | 每实例新抽奖瞬时并发上限 |
| grant-concurrency | 4 | 每实例异步发奖并发上限 |
| connection-budget | 16 | 每实例抽奖模块连接预算，需按实际连接池余量设置 |

不能只用一个速率限制所有接口：查询结果和网络重试、任务操作、新抽奖的负载不同，混用会互相挤占。连接预算也保留，用来限制并发访问数据库，不能简单由 draw-rate 推算。

新抽奖实际并发为 `min(draw-concurrency, max(1, connection-budget - grant-concurrency - 4))`；普通查询/任务与新抽奖共享这部分预算。发奖实际并发为 `max(1, min(grant-concurrency, connection-budget / 2))`；结果查询/微信回调共用固定 2 个预留并发。预算是本模块保护参数，不会修改数据库连接池大小；多实例需结合连接池配置分别评估。

## 升级旧配置

删除 `config-ttl-seconds`、`list-ttl-seconds`、`result-ttl-seconds`、`refill-concurrency` 四项。它们在新版中不再绑定，改用以下规则：

| 缓存 | 保留/刷新规则 |
| --- | --- |
| 活动配置、非空奖品列表、活动 ID 映射 | 从当前时间到活动结束时间 + 7 天，不随每次访问续 7 天 |
| 抽奖结果、补发版本标记 | 按受理快照中的活动结束时间 + 7 天；保留原补发防旧值覆盖保护 |
| 门店活动列表 | 跨多个活动，300～330 秒缓存；新增/修改/启停/范围调整通过列表版本号主动失效 |
| 空奖品列表/不存在的配置 | 最多 15 秒短期负缓存，不长时间缓存异常/空数据 |
| 配置缓存回源 | 每实例最多 4 个并发 |
| 库存、次数等运行缓存 | 沿用原清理任务：活动结束且流水结清均满 7 天、没有待处理任务才能清理 |

活动保留期已过时，配置/结果直接读取持久化数据，不再生成长期展示缓存；缺失结束日期的历史数据仅回退到 30 分钟。配置修改仍通过版本发布生效。结果缓存过期不决定发奖是否完成，也不删除持久化记录。部署前已有的展示缓存沿用其原 TTL，重新加载或发布时使用新版规则。

列表缓存过期不是定时查询，只有后续请求访问才回源。新版本发布成功后，下次请求使用新键加载，不用等五分钟。当前发布发生在事务提交后，由异步执行器处理；后台轮询每 3 秒补偿失败发布，失败后的重试间隔为 10 秒，所以不承诺保存后第一瞬间必定可见。Redis 故障或发布暂缓时，TTL 用于防止旧列表长期不刷新；持续故障时接口也可能失败。

如果旧环境曾自定义这四项，升级后会改用上述规则，需要在上线前核对。其余旧配置继续有效；例如已有 `member-draw-rate: 2` 可直接保留，不用改回示例中的 1。没有读取或发布实际 Nacos 配置，没有执行数据库脚本。
